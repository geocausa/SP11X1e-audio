# Dolby integration status — 2026-08-08

## Purpose

This is the integration-facing status after reconciling the accepted Aug-2
baseline, the Aug-5/6 Dolby completion research branch, and the state-pinned
Aug-7 Windows oracle evidence.

It is intentionally shorter and stricter than the chronological RE notes.
Historical findings remain useful evidence, but production decisions should
start here and follow the linked corrections.

## Accepted lower baseline

The protected non-Dolby Linux audio graph from `main` remains the control. Dolby
work is an overlay above that baseline; it must not hide regressions in the
kernel, AudioReach topology, SoundWire path, WSA884x configuration or speaker
protection lifecycle.

## Current experimental Dolby implementation

The current production-source candidate is:

```text
dolby-port/sp11_dolby_windows_chain_ladspa.c
```

It hosts the original ARM64 SP11 Windows DSP order:

```text
DolbyAPOvlldp150 -> DolbyApoVr
```

through the verified PE/runtime shims. Private vendor DLLs are supplied locally
and are hash-gated by:

```text
deploy/dolby/build-production.sh
```

The repository does not redistribute those DLLs.

## What is now proved

The following points have direct evidence and are suitable as engineering
constraints:

1. The live Windows Dolby speaker path contains VLLDP followed by VR in the
   recovered execution order.
2. The current Linux host can execute the original ARM64 VLLDP and VR code and
   reproduce substantial portions of the Windows behavior.
3. Stereo virtualizer bypass for the SP11 two-channel endpoint is a real Windows
   policy and is represented in the host.
4. The old May loud-75-Hz odd-harmonic fingerprint is generated by VLLDP's final
   sample-domain limiter when the limiter is driven above its normal ceiling.
5. A state-pinned Aug-7 Dynamic Windows run reproduces that fingerprint with
   `peak-level=0`, `system-gain=0`, negative endpoint-derived postgain and the
   normal VLLDP ceiling.
6. In that run the VLLDP final limiter is directly observed attenuating, with
   envelope `1.0551169`, current gain `0.9306418` and target gain `0.9266025`.
7. The same dump shows the inner VLLDP input staging already near full scale
   (`peak 0.9998694`) while the deterministic source step is approximately
   `-3 dBFS`.
8. The decoded 480 -> 256 inner adapter is a direct copy and therefore cannot
   create that ~3 dB increase.

The detailed Aug-7 evidence is:

```text
docs/findings/2026-08-07-STATE-PINNED-DYNAMIC-VLLDP-PRELIMITER-DRIVE.md
```

## What is not proved

The current Linux candidate is still not certified one-to-one with Windows for
arbitrary content, transitions and lifecycle state. In particular, the final
built-in-speaker completion gate still depends on downstream AudioReach/WSA8845
state and physical listening, not only the Dolby waveform.

The older hypotheses that the pre-VLLDP discrepancy was a blanket ~3 dB gain or
an unknown L/R matrix are now **closed/rejected**. Later controlled Windows
captures prove source amplitude is unchanged at VR input, the level/state-
dependent increase occurs inside `DolbyApoVr`, and the valid VR output bytes are
exactly the bytes delivered to VLLDP. See:

- `docs/findings/2026-08-12-WINDOWS-VR-OWNS-PRE-VLLDP-DRIVE.md`
- `docs/findings/2026-08-12-WINDOWS-VLLDP-STEREO-MATRIX-FALSIFICATION.md`

## Resolution of the former “remaining decisive experiment”

The Aug-8 matrix experiment described by older revisions of this document has
been completed and should no longer be treated as the next code-changing
milestone. The later evidence establishes the ordinary stereo path as:

```text
source PCM
  -> VR input staging (source amplitude preserved)
  -> DolbyApoVr (state/level-dependent processing)
  -> VR output staging
  == VLLDP input staging
  -> DolbyAPOvlldp150
```

Separate Aug-9/10 research also proved that the original ARM64 Dolby
ASAR/HRTF+DAP objects can be hosted on Linux and staged a genuine Windows
Spatial Audio object oracle. That work is useful provenance and future spatial
scope, but ordinary two-channel built-in-speaker parity must not be confused
with a spatial-object/HRTF completion requirement. See:

- `docs/findings/2026-08-09-ASAR-WINDOWS-DOLBY-LINUX-HOST-BREAKTHROUGH.md`
- `docs/findings/2026-08-09-ASAR-DAX-LIFECYCLE-AND-CORE-STATE-CLOSURE.md`
- `docs/findings/2026-08-10-WINDOWS-GENUINE-SPATIAL-OBJECT-ORACLE-STAGED.md`

## Repository/publication policy

The integrated public branch follows these rules:

- no vendor DLLs, process dumps or captured WAVs in Git;
- no compiled `.so` products in Git;
- raw evidence under `artifacts/raw/` stays local;
- public findings carry exact SHA-256 identities and reproducible parsers;
- tests that require private evidence skip explicitly when the bundle is absent;
- public unit tests must pass from a fresh clone;
- operator/debugger handoffs are not published because they may contain
  transient transport details;
- production paths must not depend on one developer's home-directory layout.

## Merge/deployment gates

A Dolby code change is ready for `main` only if:

1. the Windows behavior being implemented is directly observed or uniquely
   implied by stronger evidence;
2. the change is encoded as the actual operation, not a curve-fit workaround;
3. public tests pass from a fresh clone;
4. private evidence regressions pass when the local capture corpus is present;
5. the production build verifies the exact private DLL hashes;
6. finite-output, chunk-boundary, bypass and profile-lifecycle checks pass;
7. known-input waveform differences are measured and explained;
8. deployment remains rollback-safe and does not overwrite the accepted lower
   baseline.

## Current engineering decision

The old Aug-8 “recover an unknown stereo matrix” target is retired. The Dolby
stereo drive/localization question is closed strongly enough that current
built-in-speaker work should remain downstream: exact AudioReach/LPASS/WSA8845
producer-consumer semantics, demand lifecycle and physical parity. Do not add a
blanket gain or psychoacoustic substitute to compensate for a hardware-side
mismatch.

The ASAR/spatial-object branch remains valuable and its final public findings
and native Windows oracle source are preserved in the canonical branch, while
the full exploratory harness branch remains archived for provenance.
