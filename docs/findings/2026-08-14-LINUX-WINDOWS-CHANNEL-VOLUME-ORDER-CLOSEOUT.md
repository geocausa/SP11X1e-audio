# Linux/Windows channel-ordered endpoint-volume closeout

Date: 2026-08-14

## Result

The remaining structural difference in the live Windows endpoint-volume path is
closed on the isolated SP11 Linux candidate.

Fresh Windows KDNET had proved one stereo master-volume gesture is delivered to
qcadcm as two SetVolume calls:

```text
upward:
  L=new, R=old -> mixed-state GainStep
  L=new, R=new -> final GainStep

downward:
  L=new, R=old -> mixed-state GainStep
  L=new, R=new -> final GainStep
```

Linux now reproduces that sequence exactly while preserving the already-proved
Windows lifecycle: VLLDP postgain remains frozen for one Dolby/filter-chain
generation and each live SetVolume call sends final `0x4a63/0x08001038` before
the selected `0x489e` GainStep calibration.

## Maximum TLV-size gate

The extended control's maximum shape is:

```text
8-byte ALSA TLV header
+ 8 bytes left/right Q28
+ 272-byte GainStep delta
= 288 bytes
```

A live 12% -> 25% -> 12% gate exercised this exact extended row:

```text
25% final_q28=0x0182aff5 GainStep 3 delta=272 sequence=windows-lr:3->3
12% final_q28=0x00702a69 GainStep 1 delta=216 sequence=windows-lr:3->1
```

No `-EINVAL`, DSP error or fail-quiet fallback occurred. This closes the
capacity corner case that had affected the earlier 284-byte single-Q28
candidate lineage.

## Consequence

The live endpoint-volume control path is no longer an open structural
Windows/Linux difference:

- VLLDP generation lifecycle matches;
- final `0x4a63` Q28 actuation matches;
- per-channel left-first/right-second ordering matches;
- mixed-state and final GetGraphCkv/GainStep policy matches;
- maximum extended TLV size is live-proven;
- downstream WSA/protection state remains fault-free.

Do not revisit simultaneous-vs-channel-ordered volume as the explanation for a
remaining physical difference. The next gates are the corrected-topology
physical listening verdict and seek/discontinuity behavior, which are distinct
from ordinary live endpoint-volume sequencing.
