# LPASS WSA v2.5 softclip address and SP11 policy correction

Date: 2026-08-14 (Europe/London)

## Finding

The live SP11 WSA macro is the LPASS codec v2.5 register layout.  The Linux
driver correctly derives each softclip clock/CRC address from the versioned
layout (`0x640` and `0x660`), but `wsa_macro_config_softclip()` derives the
enable address from the fixed v2.1 constant `0x604`.

For v2.5 the real softclip control registers are `0x644` and `0x664`.  The
old calculation therefore targets `0x604` and `0x624`, which are
`COMPANDER1_CTL9` and `COMPANDER1_CTL17` in the v2.5 layout.

The running `7.1.5-sp11-render-parity-v3+` readback proves the defect is live:

```text
register  live  v2.5 meaning                 expected inactive/default
0x0118    0x03  both softclip mux bits        0x00 when unused
0x0604    0x01  COMPANDER1_CTL9               0x00
0x0624    0x25  COMPANDER1_CTL17              0x24
0x0640    0x01  softclip0 clock/CRC            clock on
0x0644    0x38  real softclip0 control         bit 0 remains off
0x0660    0x01  softclip1 clock/CRC            clock on
0x0664    0x38  real softclip1 control         bit 0 remains off
```

ALSA simultaneously reported both `WSA_Softclip Enable` controls as on.  This
is direct register evidence that the Linux-only UCM policy never enabled the
two hardware softclip blocks.  It instead changed two coefficients in only
the second macro compander while routing through clocked but inactive
softclip blocks.

The same hard-coded v2.1 base remains in upstream Linux master as inspected on
2026-08-14; this is not an SP11 branch-integration error.

## Correction

Patch `0053-ASoC-lpass-wsa-macro-fix-v2.5-softclip-address.patch` derives the
control address from `wsa->reg_layout->softclip0_reg_base + 4`, preserving the
existing per-version second-block stride.

The SP11 UCM explicitly selects zero for both softclip controls.  This is the
parity-safe policy because:

1. no retained Windows transaction proves that the LPASS softclip block is
   enabled for ordinary DEFAULT speaker playback;
2. the previous Linux enablement was introduced as a local loudness/safety
   experiment rather than recovered Windows behavior; and
3. disabling it removes no protection that was actually active on v3.  The
   evidence-backed WSA macro companders, WSA8845 COMP/BOOST/DAC/PBR/VISENSE,
   AudioReach SP/SPVI and CPS paths remain enabled.

This correction is evidence-backed, but it is not by itself a claim that the
remaining W03 tonal mismatch is solved.
