# SP11 WSA macro pre-sync state closeout

Date: 2026-08-15
Status: GREEN for first-MCLK reset/cache-sync hypothesis; later runtime producer configuration remains OPEN

## Question

Could Linux be corrupting a Windows-equivalent WSA-macro producer state at first MCLK by syncing generic `wsa_defaults + wsa_defaults_v2_5` from `REGCACHE_FLAT` into the hardware?

This became the strongest lower-hardware hypothesis after the rejected `DRE_CTL_1=0` cold boot exposed ugly/unsafe speaker output while ordinary CPS-v3 playback remained CSR-assisted.

## Critical common-firmware fact

Windows and Linux use the exact same Microsoft Denali ADSP image:

- file: `qcadsp8380.mbn`
- size: 22,092,168 bytes
- SHA-256: `921870a839ee2aba647b04598d62ed96f3d2d5dfbb2499fc842f9a6ff0e0da13`
- build: `ADSP.HT.5.9-00810-HAMOA-1_20250226_211949`

The exact Windows image was recovered from the installed Surface ADSP driver package. Linux `/lib/firmware/qcom/x1e80100/microsoft/Denali/qcadsp8380.mbn` hashes identically. Firmware-version drift is therefore not a valid explanation for the WSA producer mismatch.

The firmware's stripped Hexagon ELF hardware map also identifies the ADSP-local WSA aperture and sub-blocks:

- WSA macro: `0x00b00000`
- WSA TOP: `0x00b00080`
- RX0 / RX1: `0x00b00400` / `0x00b00480`
- BOOST0 / BOOST1: `0x00b00500` / `0x00b00540`
- COMPANDER0 / COMPANDER1: `0x00b00580` / `0x00b005e0`
- WSA SoundWire master: `0x00b10000`

An early Windows KD probe using `!dd [uc] 06b00580 L1` returned `Physical memory read ... failed` without crashing. A later repeat of the same uncached one-word read caused fatal bugcheck `0x124`. Direct APPS/KD WSA-macro MMIO is therefore not merely blocked but non-deterministically unsafe and is permanently excluded as a Windows oracle. See `2026-08-15-WINDOWS-WSA-MACRO-DIRECT-MMIO-UNSAFE.md`.

## Linux mechanism under test

The native `lpass-wsa-macro` driver initializes `REGCACHE_FLAT` from static version-specific defaults. On the first WSA MCLK user it already performs:

```
clk_prepare_enable(wsa->mclk)
    -> wsa_macro_mclk_enable()
       -> regcache_mark_dirty()
       -> regcache_sync()
       -> internal MCLK / FS counter enable
```

This gives Linux a theoretical opportunity to overwrite firmware/silicon state before normal playback.

## Read-only observation candidate

An isolated CPS-v3 initramfs candidate overrode only `snd-soc-lpass-wsa-macro` with a signed trace-only module. The candidate made no new writes and did not alter DRE, CSR, SoundWire, PipeWire, UCM, or AudioReach behavior.

Candidate identity:

- srcversion: `6CAE2EF0203C16B82CF0892`

- signature key: `5A:58:B6:3A:CA:17:D4:5F:02:D0:58:3E:39:7E:39:87:55:B5:62:47`
- uncompressed SHA-256: `d125f1c3d5b00d0b1848518e67c2e0df5fdba43a92cf529aa501a1553c413d49`

The module saved the already-ioremapped WSA macro base and used `readl_relaxed()` to log a bounded set of TOP/RX/BOOST/COMP registers immediately before and immediately after the existing first-MCLK `regcache_sync()`. The external WSA MCLK vote was already enabled by the existing call path before either snapshot.

The boot produced 74 trace lines covering 37 registers before and after sync.

**All 37 selected registers were byte-for-byte identical before and after `regcache_sync()`. There were zero differences.**

## Interpretation

The first-MCLK cache-sync corruption theory is closed for the selected WSA producer state. Linux is not replacing a distinct firmware/silicon WSA configuration with its generic static defaults at that boundary; the hardware already contains those values before the sync.

This also weakens the temptation to copy the older Qualcomm downstream `wsa_macro_reg_init[]` wholesale. Those older downstream values remain useful historical evidence that native WSA integration has varied, but they are not justified as SP11/Windows runtime values by the first-MCLK state.

## What remains open

This result does **not** prove later Windows runtime WSA-macro configuration equals Linux. The rejected COMP-only/DRE=0 Linux state can still fail because Windows later programs or drives the producer differently during endpoint/stream configuration.

The remaining lower-path question is now specifically:

```
common Microsoft qcadsp8380 firmware
        -> endpoint/device runtime configuration
        -> WSA RX / compander / boost producer behavior
        -> DP2 COMP sideband semantics/content
        -> WSA8845 COMP/DRE consumer
```

The next work must target the later Windows runtime configuration/data path rather than reset defaults, first-MCLK ordering, or another isolated amp register.
